Summary

Hosted cluster creation currently takes 10-15 minutes depending on platform. This proposal identifies 4 changes that together can reduce creation time by approximately 75-215 seconds (roughly 1-3.5 minutes) on cloud platforms. Each change is independent and can be implemented, tested, and merged as a standalone PR. All changes target the control-plane-operator (CPO) reconciliation flow and the v2 component framework — no user-facing API changes.

  1. Decouple infra-independent work from the infrastructure gate — start etcd, PKI, and featuregate-generator before LB IPs are ready (~60-110s saved)
  2. Reduce infra requeue interval — drop the gate requeue from 1 minute to 15 seconds (~15-30s saved)
  3. Framework-native image pre-pulling — pre-pull critical-path images via init containers on cold nodes (~0-60s saved)
  4. In-memory dependency propagation — propagate component availability within a single reconcile pass (~0-15s saved; larger benefit during upgrades)
  5. Creation time metrics — add Prometheus milestones to measure and track improvements

Problem Statement

During hosted cluster creation, the CPO's update() function in hostedcontrolplane_controller.go:1073 follows a strictly serial flow:

reconcileInfrastructure()        -- create LB Services
reconcileInfrastructureStatus()  -- check if LBs have IPs
  |
  +-- if !IsReady() --> return RequeueAfter: 1 minute  <-- GATE
  |
reconcileCPOV2()
  +-- reconcilePKI()             -- generate ~58-63 certs depending on platform (serial)
  +-- for each component:        -- ~40 registered, ~30-38 active per cluster (serial)
        checkDependencies()      -- List API call per component
        update() or skip
        reconcileComponentStatus()

This flow has several compounding inefficiencies:

  1. The infra readiness gate blocks ALL downstream work — including etcd, PKI, and featuregate-generator, which have no dependency on LoadBalancer IPs. LB provisioning takes 2-5 minutes on cloud platforms. During that entire window, the CPO does nothing.
  2. The gate requeues at 1-minute intervals, while the rest of the controller uses 15-second intervals when not ready. This adds up to 45 seconds of unnecessary polling lag.
  3. The component dependency framework evaluates dependencies by listing ControlPlaneComponent CRs from etcd. A component becoming available in one reconcile pass is only visible to dependents in the next pass (15 seconds later). With a 4-tier dependency DAG (etcd → KAS → OAPI → 15+ leaf components), this adds scheduling delay during initial creation.
  4. On management cluster nodes that haven't previously hosted a control plane, critical-path images are pulled on-demand, adding serial pull latency to component startup.

Proposal 1: Decouple Infra-Independent Work from the Infrastructure Gate

60-110s saved Medium Risk CNTRLPLANE-3497

The savings are bounded by etcd startup time (~60-90 seconds), not by the full LB provisioning window (2-5 minutes). KAS requires both a LoadBalancer IP and a ready etcd before it can start. By starting etcd earlier, we overlap its startup with LB provisioning — but etcd startup is the shorter of the two, so it sets the ceiling. An additional 10-20 seconds is saved by pre-generating 59 PKI certs before the gate, removing them from the post-gate critical path.

Problem

The infra readiness gate at hostedcontrolplane_controller.go:1088 blocks everything until all LoadBalancer Services have external IPs. A maintainer TODO already flags this:

// Block here until infra status reports readiness
// TODO(dmace): This seems a bit heavy handed vs. making more granular bits no-op if
// they don't have the specific required inputs

The following work has zero dependency on LB IPs but is currently blocked:

  • etcd StatefulSet creation and pod startup (depends on nothing)
  • featuregate-generator Job (depends on nothing)
  • All but 3 of ~58-63 PKI operations (only KAS server cert, konnectivity cluster cert, and OAuth server cert need external addresses for SANs; total count is platform-dependent)
  • Root CA, etcd CA, all etcd certs, all client certs, service account signing key (depend on nothing)

Evidence

PKI address usage is confined to exactly 3 cert reconciliation calls:

CertAddress fieldFile:Line
KAS server certExternalAPIAddresshostedcontrolplane_controller.go:1380
Konnectivity cluster certExternalKconnectivityAddresshostedcontrolplane_controller.go:1476
OAuth server certExternalOauthAddresshostedcontrolplane_controller.go:1501

All other certs in reconcilePKI() use only internal addresses (service CIDRs, namespace-based DNS names, node internal API server IP) which are known at HostedControlPlane creation time.

The etcd component's dependency list (in support/controlplane-component/status.go:30) shows it is explicitly excluded from the KAS dependency:

componentsExcludedFromKubeAPIServerDependency = sets.New(
    etcdComponentName,
    featureGateGeneratorComponetName,
    ...
)

Neither etcd nor featuregate-generator access InfraStatus in their adapt functions (verified: grep -rn 'InfraStatus' v2/etcd/ v2/fg/ returns no matches).

Design

Two changes: split PKI into infra-dependent and infra-independent phases, and extend the component framework to support infrastructure-independent components.

The current reconcilePKI() function (line 1809) is split into two functions.

Important: reconcileKASCerts (line 1840) contains both infra-dependent certs (KAS server cert at line 1380) and infra-independent certs (SA signing key at line 1401, KAS client certs). Similarly, reconcileKonnectivityCerts (line 1848) contains both the infra-dependent konnectivity cluster cert (line 1476) and infra-independent certs (konnectivity signer CA, server, client, agent). These functions must be split internally — the infra-dependent cert calls are extracted into reconcilePKIPostInfra, while the remaining calls stay in reconcilePKIPreInfra.

Rather than bypassing the component framework with a special reconcilePreGateComponents() function, extend the framework itself with the concept of infrastructure independence.

Add WithInfraIndependent() builder option (support/controlplane-component/builder.go):

// WithInfraIndependent marks a component as not requiring infrastructure
// endpoints (LoadBalancer IPs). Infra-independent components are reconciled
// before the infrastructure readiness gate.
func (b *controlPlaneWorkloadBuilder[T]) WithInfraIndependent() *controlPlaneWorkloadBuilder[T] {
    b.infraIndependent = true
    return b
}

Add field to controlPlaneWorkload (support/controlplane-component/controlplane-component.go):

type controlPlaneWorkload[T] struct {
    // ... existing fields ...
    infraIndependent bool
}

func (c *controlPlaneWorkload[T]) IsInfraIndependent() bool {
    return c.infraIndependent
}

Add to the ControlPlaneComponent interface:

type ControlPlaneComponent interface {
    Name() string
    Reconcile(cpContext ControlPlaneContext) error
    IsInfraIndependent() bool
}

The update() function runs the component loop twice — once for infra-independent components (before the gate), and once for the rest (after the gate):

func (r *HostedControlPlaneReconciler) update(ctx context.Context, ...) (reconcile.Result, error) {
    // Phase 1: Infrastructure-independent work
    if err := r.reconcileInfrastructure(ctx, hcp, createOrUpdate); err != nil {
        return reconcile.Result{}, fmt.Errorf("failed to ensure infrastructure: %w", err)
    }

    if err := r.reconcileDefaultServiceAccount(ctx, hcp, createOrUpdate); err != nil {
        return reconcile.Result{}, fmt.Errorf("failed to reconcile default service account: %w", err)
    }

    if _, exists := hcp.Annotations[hyperv1.DisablePKIReconciliationAnnotation]; !exists {
        if err := r.reconcilePKIPreInfra(ctx, hcp, createOrUpdate); err != nil {
            return reconcile.Result{}, fmt.Errorf("failed to reconcile pre-infra PKI: %w", err)
        }
    }

    // Reconcile infra-independent components (etcd, featuregate-generator)
    if err := r.reconcileInfraIndependentComponents(ctx, hcp, releaseImageProvider,
        userReleaseImageProvider); err != nil {
        return reconcile.Result{}, fmt.Errorf("failed to reconcile infra-independent components: %w", err)
    }

    // Phase 2: Infrastructure-dependent work
    infraStatus, err := r.reconcileInfrastructureStatus(ctx, hcp)
    if err != nil {
        return reconcile.Result{}, fmt.Errorf("failed to look up infra status: %w", err)
    }
    if !infraStatus.IsReady() {
        r.Log.Info("Waiting for infrastructure to be ready before proceeding")
        return reconcile.Result{RequeueAfter: hcpNotReadyRequeueInterval}, nil
    }

    // Infra-dependent PKI (3 certs)
    if _, exists := hcp.Annotations[hyperv1.DisablePKIReconciliationAnnotation]; !exists {
        if err := r.reconcilePKIPostInfra(ctx, hcp, infraStatus, createOrUpdate); err != nil {
            return reconcile.Result{}, fmt.Errorf("failed to reconcile post-infra PKI: %w", err)
        }
    }

    // Remaining components (need infraStatus)
    if err := r.reconcileCPOV2(ctx, hcp, infraStatus, releaseImageProvider,
        userReleaseImageProvider); err != nil {
        errs = append(errs, err)
    }
    // ...
}

The reconcileInfraIndependentComponents function filters r.components for those where IsInfraIndependent() == true and constructs a ControlPlaneContext without InfraStatus. The main reconcileCPOV2 loop skips infra-independent components since they were already reconciled.

Etcd and featuregate-generator component registration (in their respective component.go files):

// v2/etcd/component.go
func NewComponent() controlplanecomponent.ControlPlaneComponent {
    return controlplanecomponent.NewDeploymentComponent(...).
        WithInfraIndependent().
        // ...existing options...
        Build()
}

Unmanaged Etcd

When hcp.Spec.Etcd.ManagementType == hyperv1.Unmanaged, the etcd component's predicate returns false and the framework calls delete(). The reconcileInfraIndependentComponents function must check this: skip the etcd component dispatch when etcd is unmanaged, and instead run reconcileUnmanagedEtcd() (line 1182) in its place. The unmanaged etcd path does not create a StatefulSet and has no infra dependency.

Safety: Preventing Future InfraStatus Access

To prevent future contributors from accidentally accessing InfraStatus in an infra-independent component, the ControlPlaneContext passed to pre-gate components should have InfraStatus set to a zero-value struct. Add a unit test per infra-independent component that verifies it reconciles successfully with a zero-value InfraStatus.

As an additional safeguard, the WorkloadContext (the downcast of ControlPlaneContext available to adapt functions) could omit the InfraStatus field entirely, requiring components that need infra data to access it through a separate interface. This is a larger refactor and can be deferred.

Risks & Mitigations

Risk: PKI certs generated with empty external addresses could be picked up by components before post-infra certs are generated.
Mitigation: The 3 infra-dependent certs are created in separate Secrets. ReconcileSignedCert at support/certs/tls.go:347 checks ValidateKeyPair and returns early if the cert is already valid. Pre-infra certs won't be regenerated post-infra, and post-infra certs won't exist until the gate passes.
Risk: etcd pods start but fail because their certs don't exist yet.
Mitigation: Pre-infra PKI runs before infra-independent component reconciliation. All etcd certs are generated in reconcileEtcdCerts() which is part of the pre-infra phase. The etcd StatefulSet won't schedule until its cert Secrets exist as volume mounts.
Risk: Future contributor adds InfraStatus access to an infra-independent component without compile-time error.
Mitigation: Unit test per infra-independent component verifying reconciliation with zero-value InfraStatus. The WithInfraIndependent() builder option makes the contract explicit in the component's registration code.

Testing

  • Unit test: reconcilePKIPreInfra() generates all expected certs with empty external addresses
  • Unit test: reconcilePKIPostInfra() generates exactly 3 certs with real addresses
  • Unit test: each infra-independent component reconciles with zero-value InfraStatus
  • Unit test: unmanaged etcd path is skipped in infra-independent component dispatch
  • E2E: measure time from HCP creation to etcd pod Running (should be overlapped with LB provisioning)
  • E2E: measure total cluster creation time

Proposal 2: Reduce Infrastructure-Not-Ready Requeue Interval

15-30s saved Low Risk CNTRLPLANE-3495

Problem

When infraStatus.IsReady() returns false, the controller requeues after 1 minute (hostedcontrolplane_controller.go:1090):

return reconcile.Result{RequeueAfter: time.Minute}, nil

The rest of the controller uses hcpNotReadyRequeueInterval = 15 * time.Second (line 151) when the HCP is not ready. The 1-minute interval for infrastructure readiness is inconsistent and adds up to 45 seconds of unnecessary latency between when a LoadBalancer gets its IP and when the CPO notices.

Evidence

The hcpNotReadyRequeueInterval constant is already defined at line 151 and used at line 716 for the general not-ready case. The infrastructure requeue at line 1090 uses a hardcoded time.Minute instead of this constant — this appears to be an oversight rather than an intentional choice, since there is no comment explaining why infrastructure needs a longer interval.

LoadBalancer IP assignment is an instantaneous state change (the cloud provider assigns the IP, the Service controller updates the status). There is no benefit to polling less frequently — the CPO should detect the change as quickly as possible.

Design

Replace the hardcoded time.Minute with hcpNotReadyRequeueInterval:

if !infraStatus.IsReady() {
    r.Log.Info("Waiting for infrastructure to be ready before proceeding")
    return reconcile.Result{RequeueAfter: hcpNotReadyRequeueInterval}, nil
}

This is a one-line change.

Additional Consideration: Watch-Based Approach

The CPO already watches Services through the component framework's informer cache. If this watch covers LoadBalancer status subresource changes, the informer cache update should trigger a reconciliation automatically, making the requeue interval purely a safety net. Worth verifying — if so, the 15-second interval is more than adequate. Adding a dedicated watch on Service status changes could be a follow-up to eliminate polling entirely.

Risks & Mitigations

Risk: Increased reconciliation frequency during LB provisioning (4x more reconciles per minute).
Mitigation: Each reconcile pass when infra is not ready is cheap — it calls reconcileInfrastructureStatus() which does a handful of Service GETs, then returns immediately. After Proposal 1 lands, the pre-gate work (PKI, etcd) is also idempotent and skips quickly on subsequent passes.

Testing

  • Unit test: verify the requeue result uses hcpNotReadyRequeueInterval when infra is not ready
  • E2E: measure time between LB IP assignment and first post-gate reconcile pass

Proposal 3: Framework-Native Image Pre-Pulling for Critical-Path Components

0-60s saved (cold nodes) Low Risk CNTRLPLANE-3499

This proposal uses a framework-native approach that extends the existing component init container pattern rather than introducing a new controller and DaemonSet, achieving similar benefits for the common case with less operational overhead.

Problem

A hosted cluster control plane pulls approximately 50 distinct container images from the OCP release payload. All workloads use imagePullPolicy: IfNotPresent (set at support/controlplane-component/defaults.go:574 for main containers; init containers must set it explicitly). The first hosted cluster created on any management cluster node pays the full image pull cost for all critical-path images.

Critical-path images that block cluster readiness:

  • etcd — blocks KAS startup (tier 1)
  • hyperkube (KAS/KCM/scheduler) — blocks everything in tier 2+
  • openshift-apiserver — blocks 15+ components in tier 4
  • cluster-version-operator — has 2 init containers that extract the payload
  • token-minter — sidecar injected into most control plane deployments

Evidence

The only existing pre-pull mechanism is a KAS-specific init container at v2/kas/deployment.go:430-451 that runs /bin/sh -c echo to force the KAS image onto the node. This approach has two problems: (1) it only helps KAS, and (2) the init container adds overhead to the KAS startup critical path.

Management cluster nodes typically already have most OCP images cached from previous hosted control planes. The pre-pull optimization only helps on genuinely cold nodes (fresh scale-up events, new OCP version introduction). In steady-state operations with consistent release versions, warm nodes already have images cached.

Design

Extend the component framework to allow components to declare images that should be pre-pulled via init containers on their workload pods. Since etcd is tier 1 and deploys first, its StatefulSet init containers can pre-pull downstream critical-path images (hyperkube, OAPI, CVO) while etcd itself bootstraps.

// WithPrePullImages injects init containers that pull the specified images
// onto the node before the main containers start.
func (b *controlPlaneWorkloadBuilder[T]) WithPrePullImages(imageKeys ...string) *controlPlaneWorkloadBuilder[T] {
    b.prePullImageKeys = imageKeys
    return b
}

The framework resolves image keys to pullspecs via the ReleaseImageProvider and injects init containers that run /bin/true for each image. Since Kubernetes init containers run serially, these pre-pull containers complete before the main workload starts. The net effect is that downstream images are pulled during the LB provisioning window rather than on-demand after KAS starts.

func NewComponent() controlplanecomponent.ControlPlaneComponent {
    return controlplanecomponent.NewStatefulSetComponent(...).
        WithInfraIndependent().
        WithPrePullImages("hyperkube", "openshift-apiserver",
            "cluster-version-operator", "token-minter").
        Build()
}

This approach:

  • Reuses existing scheduling — no new DaemonSet or controller
  • Pulls images on the exact node where the HCP will run
  • Has zero overhead on warm nodes (IfNotPresent means the init container exits instantly if the image is cached)
  • Is self-cleaning — when the HCP is deleted, the pre-pull init containers go away
  • Handles pull secrets automatically (pod spec inherits the HCP namespace's pull secret)

Init container ordering: The pre-pull init containers should be appended after any existing init containers (e.g., etcd's snapshot restore init container) to avoid delaying the primary workload. Since init containers run serially, each pre-pull adds image pull time. On warm nodes this is negligible (<1s per container). On cold nodes, the total pull time for 4 images is 30-60 seconds, which adds to etcd's startup time on that pod but overlaps with the LB provisioning window (2-5 minutes).

A DaemonSet-based pre-puller that runs on all management cluster nodes was considered but deferred for the following reasons:

  • Maintenance burden: Introduces a new controller in the hypershift-operator, a new DaemonSet, and lifecycle management.
  • Pull secret management: The DaemonSet would need access to the release image pull secret, which differs per HCP namespace.
  • Priority class concerns: Using system-node-critical for an optimization DaemonSet is too aggressive.
  • Limited benefit: On warm nodes (the common case), savings are zero.
  • Kubernetes native pre-pull: Kubernetes 1.33+ provides native image pre-pull capabilities.

If the framework-native approach proves insufficient, the DaemonSet approach can be revisited. The release image count cap should be configurable rather than hardcoded.

Risks & Mitigations

Risk: Pre-pull init containers add latency to etcd startup on cold nodes.
Mitigation: On cold nodes, the images would be pulled anyway when the downstream components schedule. Pre-pulling via etcd's init containers shifts the pull earlier (overlapping with LB provisioning) rather than adding net new work. On warm nodes, the init containers exit in <1 second each.
Risk: Init containers run serially, so 4 pre-pull containers mean 4 serial image pulls.
Mitigation: Each image is ~200-500MB compressed. Total serial pull time on cold nodes is 30-60 seconds. This happens during the LB provisioning window (2-5 minutes), so it's fully overlapped. The critical path is not extended.

Testing

  • Unit test: WithPrePullImages() injects init containers with correct image resolution
  • Unit test: init containers use /bin/true command and minimal resource requests
  • Unit test: init containers are appended after existing init containers
  • E2E: on a fresh node, measure time from pod scheduling to container start for KAS

Proposal 4: In-Memory Dependency Propagation Across Component Tiers

0-15s creation / 15-30s upgrades Low Risk CNTRLPLANE-3498

During initial cluster creation, the dominant latency at each tier boundary is workload startup (pod scheduling, image pull, readiness probes), not cache staleness. The controller-runtime informer cache is watch-based and typically updates within 1-2 seconds of a CR write. The in-memory map provides guaranteed immediate propagation but the practical savings during initial creation are modest. The primary benefit is during upgrades and recovery scenarios where workloads are already running but CR status may lag.

Problem

The component dependency framework checks dependencies by listing ControlPlaneComponent CRs from the management cluster's etcd (support/controlplane-component/status.go:69-91). When a component becomes available, its status CR is updated via CreateOrPatch at controlplane-component.go:195. Downstream components checking dependencies in the same reconcile pass may see stale status because:

  1. The List call at line 70 reads from the controller-runtime cache, which may not reflect the latest write yet
  2. The component's status was just updated moments ago in the same reconcile loop iteration

The component dependency DAG has 4 tiers:

Tier 1: etcd + featuregate-generator  (no dependencies)
Tier 2: kube-apiserver                (depends on etcd + featuregate-generator)
Tier 3: KCM + scheduler + OAPI + ... (depends on KAS)
Tier 4: CVO + OAuth + CNO + ...      (depends on OAPI)

Design

Add an in-memory availability map to ControlPlaneContext:

type ControlPlaneContext struct {
    // ... existing fields ...

    // intraPassAvailability tracks components that reached Available+RolloutComplete
    // during the current reconcile pass. This is a transient, single-pass cache —
    // it must not be persisted, cached, or shared across reconcile cycles.
    intraPassAvailability map[string]bool
}

Changes to checkDependencies() — after the CR-based check, also check the in-memory map:

    // In-memory propagation: check if dependencies became available
    // during this reconcile pass (not yet visible in cached List).
    if cpContext.intraPassAvailability != nil {
        for dep := range unavailableDependencies {
            if cpContext.intraPassAvailability[dep] {
                unavailableDependencies.Delete(dep)
            }
        }
    }

    return sets.List(unavailableDependencies), nil

Changes to reconcileComponentStatus() — record availability after status update:

    desiredVersion := cpContext.ReleaseImageProvider.Version()
    // ... condition checks ...

    if isAvailable && isComplete && cpContext.intraPassAvailability != nil {
        cpContext.intraPassAvailability[c.Name()] = true
    }

Initialize in reconcileCPOV2():

cpContext := ControlPlaneContext{
    // ... existing fields ...
    intraPassAvailability: make(map[string]bool),
}

Concurrency Safety

The intraPassAvailability map is safe for the current single-threaded component loop. ControlPlaneContext is passed by value, but the map is a reference type in Go — mutations in reconcileComponentStatus are visible to checkDependencies calls in subsequent loop iterations.

If the component loop ever becomes concurrent, the map would need synchronization. Consider using sync.Map as a forward-safe choice, or document the single-threaded constraint prominently.

Realistic Savings During Initial Creation

During initial creation, the practical impact per tier boundary is:

  • A component's workload is created in pass N
  • The workload takes 15-60 seconds to become Ready (pod scheduling, image pull, probes)
  • In pass N+1 (15 seconds later), the component's status is updated to Available+RolloutComplete
  • The in-memory map records this availability
  • Downstream components in the same pass N+1 can proceed immediately via the map

Without the in-memory map, downstream components would need to wait for pass N+2 (another 15 seconds) if the cache hadn't updated yet. The savings per tier boundary is 0-15 seconds, depending on cache timing. The controller-runtime informer cache is watch-based and typically updates within 1-2 seconds, so the stale-cache scenario is uncommon but not impossible under load.

The primary value of this proposal is during upgrades and day-2 reconciliation, where workloads are already running and a status CR update can immediately unblock downstream components within the same pass.

Risks & Mitigations

Risk: A component is marked available in-memory but its workload is actually failing.
Mitigation: The map only records availability when conditions are set to Available+RolloutComplete at the correct version. These conditions are based on actual workload health, not just creation.
Risk: Version skew during upgrades — old-version component is Available but not at the desired version.
Mitigation: The in-memory check includes component.Status.Version == desiredVersion, matching the CR-based check at status.go:84.

Testing

  • Unit test: checkDependencies() resolves a dependency via the in-memory map when the CR-based check returns stale data
  • Unit test: reconcileComponentStatus() populates the in-memory map only when version matches
  • Unit test: downstream component in same loop iteration can proceed when upstream is in the map
  • Unit test: in-memory map does NOT propagate availability for wrong version
  • E2E: measure number of reconcile passes needed for all components to reach Available

Proposal 5: Creation Time Breakdown Metrics

Observability Low Risk CNTRLPLANE-3496

All three staff engineer reviewers recommended adding Prometheus metrics for tracking creation time breakdown. This has standalone value beyond the other proposals — it enables validation of improvements, regression detection, and identification of future bottlenecks.

Design

var (
    hcpCreationMilestoneSeconds = prometheus.NewHistogramVec(
        prometheus.HistogramOpts{
            Name:    "hypershift_hcp_creation_milestone_seconds",
            Help:    "Time from HCP creation to key milestones during cluster provisioning",
            Buckets: prometheus.ExponentialBuckets(5, 2, 10), // 5s to ~42min
        },
        []string{"milestone", "platform"},
    )
)

Milestones to track:

MilestoneMeasured as
infra_readyTime from HCP creation to infraStatus.IsReady() == true
etcd_availableTime from HCP creation to etcd ControlPlaneComponent Available
kas_availableTime from HCP creation to KAS ControlPlaneComponent Available
oapi_availableTime from HCP creation to OAPI ControlPlaneComponent Available
hcp_availableTime from HCP creation to hostedControlPlane.Status.Ready == true

These metrics use hcp.CreationTimestamp as the base time and record the delta when each milestone is first observed. A simple map in the reconciler tracks which milestones have been recorded to avoid re-recording on subsequent reconciles.

Testing

  • Unit test: milestones are recorded once per HCP lifecycle
  • Verify metrics are registered and scraped by the existing CPO metrics endpoint

Total estimated savings: 75-215 seconds (~1-3.5 minutes) on cloud platforms. The lower bound is the sum of each proposal's minimum savings; the upper bound assumes cold nodes and maximum overlap. In practice, interactions between proposals (e.g., earlier etcd availability amplifies Proposal 4's benefits) make simple summation an approximation.

The savings are largely additive because each proposal targets a different phase of the creation timeline:

  • Proposals 1 & 2 target the LB provisioning wait (minutes 0-5)
  • Proposal 3 targets image pull time (overlaps with component startup)
  • Proposal 4 targets component tier convergence (minutes 5-10)

Note: Proposals 1 and 4 have a minor interaction. If etcd starts earlier via Proposal 1, it reaches Available sooner, which means KAS creation starts sooner. Proposal 4's in-memory propagation then helps at the KAS→OAPI and OAPI→leaf tier boundaries. The combined savings should not be calculated by simply summing individual estimates.

Platform-Specific Notes

  • KubeVirt: No LoadBalancer provisioning, so proposals 1 and 2 have minimal impact. Proposals 3-5 still apply.
  • AWS private clusters: Additional 3-8 minutes of VPC endpoint chain are NOT addressed by these proposals. That is a separate optimization opportunity.
  • Azure: PLS creation adds 30s-2min. Not addressed here but would benefit from the same gate decoupling pattern.

Implementation Order

  1. Proposal 2 (requeue interval) — trivial one-line change, can land immediately
  2. Proposal 5 (metrics) — enables measurement before making further changes
  3. Proposal 1 (decouple from gate) — highest impact, requires PKI split + framework extension
  4. Proposal 4 (in-memory propagation) — independent of proposals 1-2, touches component framework only
  5. Proposal 3 (image pre-pull) — lowest priority, framework-native approach is low-effort
