Offline engineering handbook

What should I do next?

A day-to-day engineering reference for HyperShift work using Claude Code, Cursor, Matt Pocock’s skills, and OpenShift ai-helpers. Organized around engineering states, not AI prompts.

Claude Code for reasoningCursor for implementationMatt for handover + code reviewai-helpers for OpenShift workflow
Core question: Ask "What state of engineering am I in?"—not "What model should I use?" The state determines the tool, not the other way around.
00 · Philosophy

Five principles that do not change

The tools and models will evolve. These principles remain stable. Every decision in this handbook traces back to one of them.

1

Preserve understanding over maximizing model intelligence

The goal is your understanding of the system, not the model’s. Use AI to accelerate comprehension, not to replace it.

2

Use the smallest model capable of the task

Sonnet for routine work, Cursor for implementation. Opus only when the reasoning genuinely requires it. Premium context is a scarce resource.

3

Plans are cheaper than rework

An implementation-plan.md costs minutes. A wrong implementation costs hours. Always plan before you implement.

4

Trust tests over AI

AI confidence is not evidence. Tests, compiler output, and CI are the final judges. Verification is never optional.

5

Artifacts outlive conversations

Conversations expire. Plans, handovers, reviews, and repository memory persist. Always produce a durable artifact before moving to the next state.

01 · Engineering state machine

AI tools support these states rather than defining them.

Move work through states, not one giant agent loop

The tools can change. These states remain stable. Each state should produce a durable artifact or a verified outcome before the work moves forward.

1

Investigate

Goal: explain what is happening and what remains unknown.

Output: root cause, hypothesis set, or investigation notes.

2

Clarify

Use: grill-with-docs only when requirements or terminology are materially unclear.

Skip: obvious bugs and small mechanical changes.

3

Plan

Output: implementation-plan.md with files, invariants, risks, and test strategy.

This is the durable statement of design intent.

4

Implement

Default: Cursor or Sonnet.

Feed the implementation model the approved plan, not the full investigative transcript.

5

Review

Generic review: Matt’s code-review skill.

OpenShift-specific review: ai-helpers review commands.

6

Verify

Run narrow tests first, then formatting, package verification, broader suites, and CI as justified.

AI confidence never replaces evidence.

04 · HyperShift workflows

Common work, mapped to concrete sequences

Open each workflow for the recommended path. The sequence is intentionally simple: reason, preserve context, implement, review, verify.

OCPBUGS or Jira implementation
Read Jira→Investigate→Plan→Cursor→make verify→Matt code-review→ai-helpers review→Fix + PR

Use grill-with-docs only when requirements are ambiguous. Use handover whenever the implementation crosses a session or tool boundary.

Flaky E2E investigation
Distill logs→investigation.md→Rank hypotheses→Run smallest experiment→Update evidence→Fix→Verify repeatedly

Opus is justified when the failure spans controllers, timing, rollout, or distributed state. Do not jump to a product fix before separating test flakiness from product behavior.

Incoming PR review
Read intent→Matt code-review→ai-helpers PR review→Manual principal-level reasoning→Approve / request changes

Matt provides generic structural review. ai-helpers adds OpenShift conventions and repository-specific workflow. Your manual pass decides whether the change is safe and aligned.

API or upgrade-sensitive change
grill-with-docs→Opus architecture pass→implementation-plan.md→Cursor→Matt code-review→ai-helpers→Upgrade verification

Explicitly protect API compatibility, rollout behavior, downgrade or mixed-version assumptions, and reconciliation invariants.

CI failure after implementation
Find first meaningful error→Compare local evidence→Classify product / test / infra→Smallest repair→Re-run narrow check

Do not restart the full planning workflow unless the failure invalidates the design.

Large feature or multi-PR effort
grill-with-docs→Wayfinder→Milestone plans→Cursor→Handover between milestones→Opus milestone review

Wayfinder belongs here—not on normal Jira tickets.

05 · Decision trees

Fast decisions during the workday

Should I use Opus?

Architecture, API compatibility, or cross-controller design?YesUse Opus.
Distributed timing or reconciliation bug with multiple plausible causes?YesUse Opus for investigation.
Routine implementation or mechanical refactor?NoUse Cursor or Sonnet.
Reviewing high-risk upgrade or rollout logic?YesUse Matt review with Opus.

Should I use grill-with-docs?

Acceptance criteria disputed or incomplete?YesUse it.
Terminology or ownership boundaries unclear?YesUse it.
Obvious bug with a narrow fix?NoSkip it.
Simple test update or typo?NoSkip it.

When do I hand over?

Switching Claude Code ↔ Cursor?YesRun Matt’s handover.
Stopping for a meeting, lunch, or tomorrow?YesRun Matt’s handover.
Context has become noisy or huge?YesHandover, then start fresh.
Continuing a small task in the same clean session?NoKeep going.

Which review path?

Your own implementation before commit?YesMatt code-review + ai-helpers pre-commit review.
Incoming PR?YesMatt code-review + ai-helpers PR review.
High-risk API, rollout, or concurrency logic?YesUse Opus for the Matt review pass.
Style-only concern?NoDo not spend premium reasoning.
06 · Repository memory

Stop paying models to rediscover HyperShift

This is the main custom capability that neither Matt’s skills nor generic agent workflows fully provide. Keep concise architectural memory close to the repository and update it when understanding changes.

.ai/ └── memory/ ├── hostedcluster.md ├── nodepool.md ├── control-plane-operator.md ├── reconciliation.md ├── upgrades.md ├── testing.md ├── api-compatibility.md └── ci-and-e2e.md

What belongs there

Stable concepts, important invariants, ownership boundaries, common failure modes, lifecycle diagrams, upgrade assumptions, test entry points, and hard-won debugging knowledge.

What does not

Ticket-specific status, temporary hypotheses, copied code, stale implementation details, or content already well documented elsewhere.

Rule: Repository memory should point models toward the right three files—not replace reading the code.

08 · Anti-patterns

Common ways to waste context and money

Using Opus to type code

Premium reasoning is wasted on routine implementation that Cursor can perform from a plan.

Dragging one giant conversation forward

Switching models inside a bloated context does not recover the cost. Use handover and start fresh.

Duplicating Matt’s skills

Do not maintain custom handoff and review prompts when handover and code-review already solve those problems.

Review before verification

A review pass on code that does not compile or pass narrow tests is expensive theater.

Using Wayfinder for normal tickets

Wayfinder is for multi-session, multi-PR, or sprawling work—not ordinary bug fixes.

Repository memory as stale documentation

Memory that is not maintained becomes more dangerous than no memory at all.

Better

Preserve intent in a plan, progress in handover, findings in code review, and truth in tests.

Better

Use the smallest model capable of moving the work to the next state.

09 · Prompt & skill reference

Only prompts that are not already covered by Matt or ai-helpers

There is no custom handover prompt and no custom review prompt here. Use Matt’s skills for those.

Matt’s Skills

grill-with-docs

Use only when requirements are ambiguous. Produces requirements.md with disputed terms, constraints, and acceptance criteria.

Skip for: obvious bugs, small mechanical changes, typos.

handover

Use every context switch: tool changes, model changes, meetings, end of day, different engineer. Produces handover.md.

code-review

Primary review workflow. Produces code-review.md. Do not duplicate with custom review prompts.

wayfinder

Only for epics and architecture. Multi-session, multi-PR, or sprawling investigations. Not for normal Jira tickets.

ai-helpers workflows

Implementation flow

Cursor→make verify→Matt code-review→ai-helpers pre-commit-review→Fix→PR

Incoming PR flow

Checkout branch→Matt code-review→ai-helpers PR review→Submit review

Custom prompts

Implementation planning

Investigate this change without modifying code. Produce an implementation-plan.md containing: - expected and current behavior - affected components and files - relevant invariants - proposed implementation steps - compatibility, rollout, and upgrade risks - targeted test plan - unresolved questions Use repository guidance before broad exploration. Stop if a material design decision remains ambiguous.

Flaky E2E investigation

Analyze the supplied failure evidence and update investigation.md. Maintain: - symptom and failing phase - relevant timeline - components involved - hypotheses ranked by likelihood - evidence for and against each hypothesis - completed experiments and outcomes - current confidence - the smallest next experiment that distinguishes the top hypotheses Do not propose a product fix until the evidence separates test flakiness, infrastructure failure, and product behavior.

CI evidence distillation

Distill these CI logs without diagnosing yet. Extract only: - failing jobs and tests - first meaningful error - timestamps and ordering - component or controller errors preceding failure - object states and transitions - stack traces - differences from a supplied passing run Preserve exact identifiers and error text. Remove unrelated log noise.

Repository memory update

Review this completed work for durable HyperShift knowledge. Suggest only stable additions or corrections to .ai/memory. Exclude ticket-specific status, temporary hypotheses, code excerpts, and details already documented elsewhere. For each proposed memory change, include: - target file - concise addition or correction - why it will reduce future rediscovery - evidence from the completed work
