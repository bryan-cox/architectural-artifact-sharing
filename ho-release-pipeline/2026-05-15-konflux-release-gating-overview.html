HyperShift Operator

Konflux-based Release Promotion Pipeline

A nightly, platform-independent gating system that validates HyperShift Operator images against e2e test suites before promoting them to verified repositories. This pipeline runs alongside the existing auto-release and provides managed service teams with confidence that promoted images have passed real-world validation.

Problem

  • Every merged HyperShift Operator (HO) build is auto-released to ACMD (quay.io/acm-d/rhtap-hypershift-operator) immediately after the Konflux build pipeline completes — before platform-specific test results are available.
  • Platform teams do run their own testing (ROSA regression tests, ARO HCP e2e tests), but these results do not gate the release. A bad image can be consumed by managed service teams before those tests complete.
  • The gap is timing and gating — testing exists, but the auto-release does not wait for it. There is no mechanism to promote only images that have passed platform validation.
  • Without a gated promotion path, managed service teams must independently track which images have been validated and which have not.

Solution Overview

  • Add a parallel, gated promotion path alongside the existing auto-release — a nightly pipeline tests the latest HO image and only promotes it to a verified repository if e2e tests pass.
  • Each managed service platform (ARO HCP, ROSA HCP, GCP HCP) gets its own independent promotion path, so a failure on one platform does not block others.
  • The existing auto-release to ACMD is unchanged — the new path is purely additive. Teams that depend on ACMD images continue to receive them as before.
  • ARO HCP serves as the pilot platform. ROSA HCP and GCP HCP follow the same template with their own test suites and verified repositories.
  • Extending to a new platform requires only new Konflux resource definitions — no pipeline code changes.

Dual-Path Architecture

The two paths below operate independently and in parallel. The existing auto-release (top) continues to deliver every merged build to ACMD with no changes. The new gated promotion path (bottom) adds nightly validation and only promotes images that pass e2e tests to a verified repository. Both paths originate from the same Konflux Snapshots created by the push build pipeline.

Existing Auto-Release to ACMD — unchanged, no validation gate
New Gated Promotion to Verified Repo — parallel path, e2e validated

Pipeline Phases

The gated promotion path from the architecture above breaks down into four sequential phases. Each phase is a distinct step in the nightly pipeline, and a failure at any stage prevents downstream phases from executing.

1
Trigger

A Kubernetes CronJob fires nightly at 3:15 AM UTC (offset from the hour to avoid peak load) in the crt-redhat-acm-tenant namespace. This is the entry point that kicks off the entire promotion pipeline.

CronJob
2
Resolve

The CronJob queries Konflux Snapshots labeled with the push build's PipelineRun name, selects the most recently created one, and extracts the HO container image reference (including its SHA digest). This ensures we always test the latest build from main.

Snapshot
3
Test

An IntegrationTestScenario deploys the resolved HO image and runs the HyperShift e2e test suite against it. The MVP uses HyperShift's own e2e suite from test/e2e/; later iterations add platform-specific tests (e.g., ARO HCP tests exercising Azure ARM APIs).

IntegrationTestScenario
4
Promote / Notify

If tests pass, a Konflux Release object is created referencing the tested Snapshot and the platform's ReleasePlan. Konflux's release pipeline then pushes the validated image to the verified repository. If tests fail, a Slack webhook fires with failure details so the team can investigate.

Test Outcomes

After the e2e test suite completes, the pipeline takes one of two paths depending on the result. In both cases, the existing ACMD auto-release is completely unaffected — images remain available there regardless of whether the gated promotion succeeds or fails.

Tests Pass
  1. The pipeline's finally block creates a Release object referencing the tested Snapshot and the platform's ReleasePlan
  2. Konflux's release pipeline picks up the Release and pushes the image to the verified quay repository
  3. The managed service team (e.g., ARO HCP) can safely consume the promoted image, knowing it has passed e2e validation
Tests Fail
  1. The pipeline's finally block sends a Slack webhook notification with the snapshot name, image reference, and a link to the failed pipeline run
  2. The image is not promoted to the verified repository — teams will not consume an untested image
  3. The ACMD auto-release is unaffected — the image remains available there as usual
  4. The team investigates the failure and can manually re-trigger the pipeline once the issue is resolved

Konflux Resources

The gated promotion pipeline is composed of several Kubernetes/Konflux resources that work together. All resources are created in the crt-redhat-acm-tenant namespace unless noted otherwise. Expand each item below to see the YAML definition and details.

Runs nightly at 3:15 AM UTC (offset from the hour to avoid Konflux peak load). This is the entry point for the entire promotion pipeline. It resolves the most recent Snapshot from the push build pipeline, extracts the HO container image reference, and creates a Tekton PipelineRun that executes the e2e test pipeline with the snapshot name and image as parameters.

kind: CronJob
apiVersion: batch/v1
metadata:
  name: hypershift-operator-nightly-promotion
  namespace: crt-redhat-acm-tenant
spec:
  schedule: '15 3 * * *'
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: resolve-and-test
            image: 'quay.io/konflux-ci/task-runner:v1'
            command: ["/bin/bash", "-c"]
            args:
            - |
              #!/bin/bash
              set -euo pipefail

              # Resolve the most recent Snapshot from push builds
              SNAPSHOT=$(oc get snapshot \
                --sort-by=.metadata.creationTimestamp \
                -l pac.test.appstudio.openshift.io/original-prname=hypershift-operator-main-on-push \
                -o jsonpath='{.items[-1].metadata.name}')
              HO_IMAGE=$(oc get snapshot $SNAPSHOT \
                -o jsonpath='{.spec.components[?(@.name=="hypershift-operator-main")].containerImage}')
              echo "Resolved snapshot: $SNAPSHOT"
              echo "HO image: $HO_IMAGE"

              # Create a PipelineRun to execute the e2e test pipeline
              oc create -f - <<EOF
              apiVersion: tekton.dev/v1
              kind: PipelineRun
              metadata:
                generateName: ho-release-gate-nightly-
                namespace: crt-redhat-acm-tenant
              spec:
                pipelineRef:
                  resolver: git
                  params:
                  - name: url
                    value: https://github.com/openshift/hypershift
                  - name: revision
                    value: main
                  - name: pathInRepo
                    value: .tekton/pipelines/ho-release-gate.yaml
                params:
                - name: snapshot-name
                  value: $SNAPSHOT
                - name: ho-image
                  value: $HO_IMAGE
                taskRunTemplate:
                  serviceAccountName: nightly-promotion-sa
              EOF
          serviceAccountName: nightly-promotion-sa
          restartPolicy: OnFailure

This resource wires the e2e test Tekton pipeline as a gate on Snapshots. It references a pipeline definition stored in the HyperShift repository, which allows the test pipeline to evolve alongside the code it validates. For the MVP, the pipeline runs HyperShift's general e2e suite; future iterations will add platform-specific tests.

apiVersion: appstudio.redhat.com/v1beta2
kind: IntegrationTestScenario
metadata:
  name: hypershift-ho-release-gate-aro-hcp
  namespace: crt-redhat-acm-tenant
spec:
  application: hypershift-operator
  resolverRef:
    resolver: git
    params:
    - name: url
      value: https://github.com/openshift/hypershift
    - name: revision
      value: main
    - name: pathInRepo
      value: .tekton/pipelines/ho-release-gate.yaml
  contexts:
  - name: application
    description: HyperShift e2e tests for ARO HCP promotion gating

Unlike the resources above, Release objects are not created in advance. They are generated programmatically by a Tekton finally task after the e2e tests pass. Each Release references the specific Snapshot that was tested and the platform's gated ReleasePlan. Once created, Konflux's built-in release pipeline handles the actual image push to the verified repository. The gracePeriodDays field provides a window for manual intervention if needed.

apiVersion: appstudio.redhat.com/v1alpha1
kind: Release
metadata:
  generateName: hypershift-operator-aro-hcp-
  namespace: crt-redhat-acm-tenant
spec:
  snapshot: <snapshot-that-passed-tests>
  releasePlan: hypershift-operator-ho-release-gate-aro-hcp
  gracePeriodDays: 7

The nightly CronJob runs under a dedicated service account with least-privilege RBAC. It needs read access to Snapshots and Components (to resolve the latest image), create access to PipelineRuns (to trigger the e2e test pipeline), and create access to Releases (to trigger promotion on pass). These permissions are scoped to the crt-redhat-acm-tenant namespace only.

apiVersion: v1
kind: ServiceAccount
metadata:
  name: nightly-promotion-sa
  namespace: crt-redhat-acm-tenant
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: nightly-promotion-role
  namespace: crt-redhat-acm-tenant
rules:
- apiGroups: ["appstudio.redhat.com"]
  resources: ["snapshots", "releases"]
  verbs: ["get", "list", "create"]
- apiGroups: ["appstudio.redhat.com"]
  resources: ["components"]
  verbs: ["get", "list", "patch"]
- apiGroups: ["tekton.dev"]
  resources: ["pipelineruns"]
  verbs: ["create", "get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: nightly-promotion-binding
  namespace: crt-redhat-acm-tenant
subjects:
- kind: ServiceAccount
  name: nightly-promotion-sa
roleRef:
  kind: Role
  name: nightly-promotion-role
  apiGroup: rbac.authorization.k8s.io

E2E Test Pipeline

The promotion pipeline is defined as a Tekton Pipeline at .tekton/pipelines/ho-release-gate.yaml in the HyperShift repository. It consists of five sequential tasks followed by a finally block that handles promotion or notification. Storing it in the repo ensures the test pipeline evolves alongside the code it validates.

MVP Test Coverage

Test coverage will expand in phases. The MVP starts with HyperShift's own e2e suite from test/e2e/ to validate core cluster lifecycle operations. Subsequent phases add broader version coverage and platform-specific tests co-authored with platform QE teams.

Phase 1 MVP
  • Cluster lifecycle (create/destroy)
  • NodePool scaling
  • One upgrade path
Phase 2 Full Matrix
  • Every supported CPO latest 4.y.z
  • Every CPO latest-minus-one 4.y.z
  • Every supported minor release 4.y.0
Phase 3 Platform-Specific
  • ARO HCP-specific e2e suite
  • Azure ARM API integration tests
  • Platform QE co-authored tests

Error Handling

The pipeline is designed to fail safely. No failure mode results in an untested image being promoted to the verified repository. In all failure cases, the existing ACMD auto-release continues unaffected. The table below covers expected failure scenarios and how each is handled.

Failure Impact Handling
CronJob fails to resolve Snapshot No test run, no promotion Slack alert + manual re-trigger
E2e tests fail Image not promoted to verified repo Slack alert with failure details. ACMD unaffected.
E2e tests flake Unnecessary promotion block Manual re-trigger. Future: retry logic.
Release creation fails Tested image not promoted Slack alert. Manual Release creation as fallback.
No promotion in N days Platform running stale image Stale alert (configurable threshold, default 3 days)
Manual Re-trigger

If a nightly run fails due to flakes or transient issues, the pipeline can be manually re-triggered by creating a one-off Job from the CronJob template:

oc create job --from=cronjob/hypershift-operator-nightly-promotion \
  manual-$(date +%s) -n crt-redhat-acm-tenant

Platform Extensibility

The pipeline is designed from the start to support multiple managed service platforms. Each platform gets its own independent promotion path with its own test suite and verified repository. Adding a new platform requires creating 2–3 Konflux resources — an IntegrationTestScenario, a ReleasePlan, and optionally a separate CronJob schedule. No pipeline code changes are needed.

Platform IntegrationTestScenario ReleasePlan CronJob Status
ARO HCP hypershift-ho-release-gate-aro-hcp ...-aro-hcp-verified Shared nightly Pilot
ROSA HCP hypershift-ho-release-gate-rosa-hcp ...-rosa-hcp-verified Shared or separate Future
GCP HCP hypershift-ho-release-gate-gcp-hcp ...-gcp-hcp-verified Shared or separate Future
Each platform's promotion is fully independent. A failure on one platform does not block promotion on others. The YAML examples in the Konflux Resources section above show the ARO HCP pilot instance; ROSA HCP and GCP HCP will follow the same pattern with their own resource names and verified repositories.

Open Questions

The following items need to be resolved before or during implementation. Each is tracked as a separate Jira issue where applicable.

Test infrastructure
Where do the e2e tests run? The pipeline needs a cluster with cloud credentials (Azure for ARO HCP, AWS for ROSA HCP). We need to coordinate with each platform team to get tests that can run on their infrastructure. See CNTRLPLANE-3452.
ReleasePlanAdmission
The gated ReleasePlan requires a matching ReleasePlanAdmission in the rhtap-releng-tenant namespace. This requires coordination with the releng team. What policies govern the verified repo? What approval workflows are needed?
Verified repo location
Which quay.io repository serves as the verified/promoted destination? We need to create a new quay repo that the managed service teams (ARO HCP, ROSA HCP) can also reach.
Platform e2e test integration
Bryan is working with the ARO HCP team to integrate their platform-specific e2e tests into the HyperShift repo, following the same pattern used for HyperShift's existing presubmit e2e tests.
