HyperShift V2 Lifecycle Tests — Design Spec

V2 Lifecycle Tests for Azure Self-Managed

Port the 4 remaining v1 lifecycle tests to the v2 Ginkgo framework with platform-agnostic labels and per-platform cluster mapping.

TestAutoscaling TestNodePool TestUpgradeControlPlane TestHAEtcdChaos

Goals

Port all 4 v1 lifecycle tests to v2 Ginkgo BDD test files
Tests are platform-agnostic: labels determine what runs, CI workflows determine which cluster to target
Each platform decides independently whether a test gets its own cluster or shares an existing one
For Azure self-managed: reuse the existing public cluster for autoscaling + nodepool tests, create 1 new HA cluster for upgrade then etcd-chaos (sequentially)

Out of Scope

The following v1 tests are not ported in this work:

TestCreateCluster — already covered by v2 workflow cluster creation + existing validation tests
AWS-only NodePool sub-tests — day-2 tags, spot termination, image types
KubeVirt / OpenStack-specific tests
TestNodePoolMultiArch — separate test, not in the v1 CI_TESTS_RUN filter

Design

How tests map to clusters, and what each test file covers.

Cluster Layout

The v2 CI workflow already provisions 3 hosted clusters. This work adds 1 more — an HA cluster provisioned at N-1 that first runs the upgrade test, then runs etcd chaos tests on the same upgraded cluster.

ClusterConfigLabels Run Against It
public Latest release, workers self-managed-azure-public   nodepool-autoscaling   nodepool-lifecycle
private Private topology self-managed-azure-private
oauth-lb OAuth via LoadBalancer self-managed-azure-oauth-lb
✨ upgrade N-1 release image, HA control plane control-plane-upgrade → etcd-chaos (sequential)

✨ = new cluster added by this work. Unmarked clusters already exist in the v2 CI workflow. The upgrade cluster runs control-plane-upgrade first, then etcd-chaos sequentially on the same HA cluster.

Test Labels

Each cluster runs tests matched by platform-agnostic Ginkgo labels. CI workflows map labels to clusters, so the same test code works across AWS, Azure, and GCP.

nodepool-autoscaling

Scale-up, scale-down, balancing

nodepool-lifecycle

Machineconfig, upgrades, auto-repair…

control-plane-upgrade

N-1 → latest CP upgrade

etcd-chaos

Kill / recover / corrupt members

Other platforms (AWS, GCP) can map these labels to different cluster topologies. For example, AWS might create a dedicated cluster per label instead of sharing the public cluster.

Parallelism & Safety

Because autoscaling and lifecycle tests share the public cluster, every test must be parallelism-safe.

Each test creates uniquely-named NodePools and cleans up via defer — no mutation of the default NP
CI controls parallelism via --ginkgo.procs=N per binary invocation
Upgrade and etcd-chaos run sequentially on the same HA cluster — upgrade first, then chaos. Both run in parallel with public/private/oauth-lb tests.

V2 Test Files

These labels correspond to 4 new test files under test/e2e/v2/tests/. Each follows the v2 convention: a RegisterXxxTests() function, a top-level Describe with a Label, and It blocks for each sub-test.

nodepool_autoscaling_test.go
nodepool-autoscaling

Creates its own NodePools (does not modify the cluster's default NP — unlike v1). Necessary because the cluster may be shared with other tests.

Scale Up Create autoscaling NP (min=1, max=3), deploy memory-pressure workload (Job with max pods, each requesting 50% of a node's allocatable memory), verify node count increases to max
Scale Down Delete the workload, verify node count decreases back to min
Balancing Create a second NP with autoscaling, deploy workload, verify pods are balanced across both NodePools
Cleanup: deletes created NodePools and workloads via defer

control_plane_upgrade_test.go
control-plane-upgrade

Assumes the cluster was created at N-1 release image.

  1. Record starting version from hostedCluster.Status.Version.History
  2. Patch spec.release.image to the latest release image
  3. Set ForceUpgradeToAnnotation annotation
  4. Wait for control plane component rollout 4.20+
  5. Wait for control plane version rollout 4.22+
  6. Wait for data plane (CVO) rollout
  7. Validate: feature gates, node count, no crashing pods, MachineDeployment generation = 1
Requires: E2E_LATEST_RELEASE_IMAGE, E2E_PREVIOUS_RELEASE_IMAGE
etcd_chaos_test.go
etcd-chaos

Ordered Ginkgo context — tests run sequentially. Assumes HA control plane. Runs on the upgrade cluster after the upgrade test completes.

Sub-testWhat it does
Single member recoveryDelete one etcd pod, verify recovery + data preserved
Kill random membersRepeatedly delete random pods, verify data integrity
Kill all membersDelete all etcd pods simultaneously, verify full recovery
Single member corruptionCorrupt one PVC, verify etcd auto-heals
Missing member recoveryDelete one PVC, verify etcd replaces the member
Each sub-test creates a marker ConfigMap before chaos, verifies it survives.

CI Workflow Changes

Cluster creation logic lives in the hypershift repo as a Go binary (or test command), not as inline shell scripts in openshift/release. The CI step in openshift/release simply calls this binary. This keeps cluster creation logic co-located with the tests and easier to maintain.

A Go binary in the hypershift repo handles test cluster creation. The CI step calls it instead of running hypershift create cluster azure inline. The binary:

  • Creates the upgrade cluster: N-1 release, HA control plane
  • Waits for cluster readiness
  • Writes cluster name to SHARED_DIR

This pattern mirrors how the test runner step already calls bin/test-e2e-v2 — the create-guests step just calls a different binary from the same repo.

  • Public cluster label filter adds: self-managed-azure-public || nodepool-autoscaling || nodepool-lifecycle
  • Upgrade cluster runs control-plane-upgrade first, then etcd-chaos sequentially on the same cluster
  • Public cluster timeout increases from 45m to accommodate lifecycle tests
  • OCP_IMAGE_PREVIOUS, OCP_IMAGE_N1, OCP_IMAGE_N2 passed as env vars

openshift-hypershift-main.yaml v2 job adds dependencies:

dependencies:
  OCP_IMAGE_PREVIOUS: release:initial
  OCP_IMAGE_N1: release:n1minor
  OCP_IMAGE_N2: release:n2minor

Updated to handle the additional upgrade cluster (same pattern as existing 3).

File: test/e2e/v2/tests/etcd_chaos_test.go (create)

Label: etcd-chaos   Decorator: Ordered (sequential execution)

Five sub-tests — each creates a marker ConfigMap before chaos, verifies it survives:

  1. Single member recovery — delete one pod + PVC, verify replacement
  2. Kill random members — delete random pods for 30s, verify data integrity
  3. Kill all members — delete all pods simultaneously, verify full recovery
  4. Single member corruption — corrupt WAL file, verify auto-heal via recovery job
  5. Missing member recovery — remove member via etcdctl + delete pod, verify recovery
