FIPS in HyperShift is a day-1 immutable boolean that propagates through 3 hops: HostedCluster → HostedControlPlane → Ignition MachineConfig → Worker Nodes. The setting is platform-agnostic (no AWS/Azure/KubeVirt-specific code), and ultimately results in nodes booting with the fips=1 kernel parameter.

🏛 What FIPS Means in Context

FIPS 140-2 (and its successor FIPS 140-3) is a US government standard for cryptographic modules. When a cluster runs in “FIPS mode,” the underlying operating system kernel and userspace cryptographic libraries restrict themselves to FIPS-validated algorithms and implementations.

In RHCOS (Red Hat Enterprise Linux CoreOS), enabling FIPS mode triggers:

⚙️

Kernel boots with fips=1 on the command line

🛡️

dracut-fips forces kernel crypto into FIPS mode

🔐

OpenSSL, GnuTLS, NSS operate in FIPS-validated mode

🚫

Non-FIPS algorithms disabled at the library level

⚠️
Immutable Day-1 Decision: In HyperShift, FIPS configuration is a cluster-wide, immutable, day-1 decision. It cannot be toggled after cluster creation. This is enforced by a CEL validation rule at the CRD level.

📋 API Layer: How FIPS Is Configured

HostedCluster Spec

The primary entry point is spec.fips on the HostedCluster resource.

api/hypershift/v1beta1/hostedcluster_types.go:782-788

// fips indicates whether this cluster's nodes will be running in FIPS mode.
// If set to true, the control plane's ignition server will be configured to
// expect that nodes joining the cluster will be FIPS-enabled.
// +kubebuilder:validation:XValidation:rule="self == oldSelf", message="fips is immutable"
// +optional
// +immutable
FIPS bool `json:"fips"`
Type: bool

Non-pointer boolean. Zero value (false) = FIPS off. No ambiguity between “not set” and “set to false.”

Immutable via CEL

self == oldSelf enforced at CRD schema level. Cannot be changed post-creation.

No omitempty

Always serializes — every HC YAML shows fips: false or fips: true explicitly.

HostedControlPlane Spec

The same field exists on the HostedControlPlane, the internal resource the hypershift-operator creates for the control-plane-operator (CPO).

api/hypershift/v1beta1/hosted_controlplane.go:139-141

// fips specifies if the nodes for the cluster will be running in FIPS mode
// +optional
FIPS bool `json:"fips"`
The HCP’s fips field does not have its own immutability CEL rule — it doesn’t need one because HCP resources are internal and their lifecycle is managed by the hypershift-operator controller, not directly by users.

CLI Flag

When creating clusters via the hypershift CLI, the --fips flag is available and platform-agnostic.

cmd/cluster/core/create.go:90

flags.BoolVar(&opts.FIPS, "fips", opts.FIPS, "Enables FIPS mode for nodes in the cluster")

1 HostedCluster → HostedControlPlane

The hypershift-operator’s HostedCluster controller copies spec.fips from the HostedCluster to the HostedControlPlane.

hypershift-operator/controllers/hostedcluster/hostedcluster_controller.go:2749

hcp.Spec.FIPS = hcluster.Spec.FIPS
Simple direct copy — no transformation, no conditional logic. Happens alongside other spec fields like networking, pull secrets, and SSH keys.

The ConfigGenerator.getCoreConfigs() method lists all ConfigMaps labeled hypershift.openshift.io/core-ignition-config: true. It expects 2 or 3 core ConfigMaps:

The ConfigGenerator in config.go concatenates all MachineConfig YAML from the core ConfigMaps into a single config string. The token secret’s Reconcile method in token.go then compresses the config via CompressedAndEncoded() (line 332) and stores it in tokenSecret.Data[TokenSecretConfigKey] (line 351).

config.go:278-304 (parse) · token.go:332-351 (compress & store)

ignition-server/controllers/tokensecret_controller.go:257-282

  1. Reads compressed config from the token Secret
  2. Passes it to LocalIgnitionProvider.GetPayload()
  3. Runs the MCO’s machine-config-server binary against the release image
  4. MCO renders all MachineConfigs (including 30-fips) into a single ignition config
  5. When 30-fips has spec.fips: true, the MCO includes kernel argument fips=1

RHCOS boots with fips=1:

⚙️ Kernel — FIPS module performs self-tests
🛡️ dracut-fips — validates crypto modules
🔐 OpenSSL — enters FIPS mode
💻 Workloads — all crypto uses FIPS-validated implementations

🎯 Control Plane Component Impact

Ingress Operator — The Only Explicit FIPS Consumer

control-plane-operator/controllers/hostedcontrolplane/v2/ingressoperator/deployment.go:25-29

if cpContext.HCP.Spec.FIPS {
    podspec.UpsertEnvVar(c, corev1.EnvVar{
        Name: "FIPS_ENABLED", Value: "true",
    })
}

When FIPS is enabled, the ingress operator deployment receives the FIPS_ENABLED=true environment variable. This tells the ingress operator to configure HAProxy routers with FIPS-compatible cipher suites and TLS settings.

What About KAS, etcd, and Other Components?

The codebase does not have explicit FIPS-specific configuration for kube-apiserver, etcd, openshift-apiserver, oauth-server, or other control plane pods. Here’s why:

🏢
Management Cluster Isolation

Control plane pods run on the management cluster, not on FIPS-enabled worker nodes. The management cluster’s FIPS posture is its own concern.

💻
Data Plane Focus

The hosted cluster’s FIPS setting is about the data plane (worker nodes) and the crypto expectations for nodes joining the cluster.

🔍
Runtime Detection

OCP Go binaries detect FIPS mode at runtime via the OS kernel. When running on a FIPS-enabled kernel, they automatically use FIPS-validated crypto.

🌍 Platform-Specific Considerations

✅
Key Insight: FIPS is entirely platform-agnostic in HyperShift. There is zero platform-specific FIPS code in the codebase. The --fips flag works identically across AWS, Azure, KubeVirt, OpenStack, Agent, and other platforms.

How This Differs from Standalone OpenShift

ConcernStandalone OpenShiftHyperShift
Image Selection May use FIPS-specific AMIs Same RHCOS image; FIPS activated at boot via MachineConfig
Disk Encryption FIPS may require specific algorithms Configured separately from FIPS through NodePool spec
Installer Behavior Sets OPENSHIFT_INSTALL_FIPS Ignition server replaces the installer’s MCS role
Azure AKS Management Cluster: Azure docs mention FIPS in the context of the AKS management cluster itself — that’s a separate concern from the hosted cluster’s FIPS setting. The AKS FIPS setting ensures the management cluster nodes run FIPS-compliant crypto.

Go VersionFIPS BackendMechanism
≤ 1.19 🌐 BoringCrypto Google-maintained FIPS-validated module via build tags
1.21+ 🔒 crypto/internal/fips140 Go’s native FIPS 140-3 compliance mechanism

When these binaries run on a kernel with fips=1, they detect FIPS mode (typically by reading /proc/sys/crypto/fips_enabled) and automatically restrict themselves to FIPS-validated algorithms. This is transparent to application code.
