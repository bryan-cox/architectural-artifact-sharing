Scenario 3: CPO External Route Behavior for Private Clusters

Objective: Verify the CPO correctly handles the absence of a hostname for the KAS external route — only the internal route should exist when no external DNS domain is configured.

Overall Scenario 3: PASS — All 3 checks verified.
StepCheckResultEvidence
1 kube-apiserver internal route exists PASS Route kube-apiserver-internal exists with host api.brcox-100054-hc.hypershift.local, passthrough TLS. See Appendix I and raw evidence below.
2 kube-apiserver-external-public does NOT exist PASS Error from server (NotFound) confirms route not created. See Appendix I and raw evidence below.
3 kube-apiserver-external-private does NOT exist PASS Error from server (NotFound) confirms route not created. See Appendix I and raw evidence below.

Implementation Detail

The CPO's ReconcileInfrastructure now checks whether a hostname is configured for the external KAS route. When the service publishing strategy is Route but no hostname is set (i.e., no --external-dns-domain), the CPO:

  1. Skips creating the external private route entirely
  2. Uses k8sutil.DeleteIfNeeded to clean up any obsolete external routes that may have been created previously
  3. Falls back to the KAS service's ClusterIP for status reporting when no external route exists

Raw Evidence
